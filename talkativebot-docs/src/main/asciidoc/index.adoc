== Summary

TalkativeBot is a Java 17 / Spring Boot 3 multi-module library for building *stateful, channel-agnostic conversation flows*.
It sits between your business application and messaging or AI transports: you model human-in-the-loop interactions as conversations and topics, the framework asks questions, persists pending state, and resumes when answers arrive.

The design deliberately separates orchestration from transport. The `talkativebot-core` module is Spring-free (enforced by Maven Enforcer) and owns the conversation engine; `talkativebot-spring-boot-starter` adds classpath topic scanning, auto-configuration, and optional Redis, JPA, console, and Spring Cloud Stream integrations.
Example modules demonstrate a local checkout flow (`example-console`) and a distributed joke-bot over RabbitMQ and Redis (`example-stream-redis`).

*Current version:* `{project-version}` (parent POM `talkativebot-parent`).

== What TalkativeBot Is — and Is Not

=== What it is

* A lightweight conversation *state manager* for structured human interaction
* A way to decouple business dialogue logic from chat platforms, REST controllers, and message consumers
* A multi-channel orchestration layer with pluggable input/output adapters and pending-interaction persistence

=== What it is not

* A workflow engine (no BPMN, no long-running saga orchestration beyond conversation scope)
* A chatbot platform or AI framework (no LLM integration, no NLU)
* A replacement for messaging infrastructure — it consumes and produces messages through your channels

The intended use case is applications that already have complex business logic and need a predictable layer for *ask → wait → resume* interactions without embedding that logic in channel-specific code.

== Architecture

=== Central orchestrator

`com.atchurey.tools.talkativebot.core.bot.TalkativeBot` is the single entry point for message handling and conversation execution. It implements `InputMessageHandler` and coordinates:

[cols="2,4", options="header"]
|===
| Collaborator | Responsibility

| `TopicScanner` / `TopicFactory`
| Discover `@Topic` classes and instantiate them for a conversation

| `ConversationFactory`
| Recreate conversation instances by fully qualified class name + `ConversationAddress`

| `PendingInteractionStore`
| Persist in-flight question/answer state with TTL

| `OutputChannelRegistry`
| Route outbound messages to the first matching `OutputChannel`

| `OptionSelector`
| Map inbound text to `Option` for choice questions

| `ConversationStartRegistry`
| Resolve new conversations when no pending interaction exists

| `ConversationRuntimeRegistry`
| Per-conversation-type shared resources (HTTP clients, repositories)
|===

Key public operations:

* `play(Conversation)` — hydrate runtime, invoke `conversation.play()`
* `ask(conversation, topic, question)` — save `PendingInteraction`, send `OutgoingMessage.question(...)`
* `handle(IncomingMessage)` — resume pending interaction or start via `ConversationStartResolver`

=== Conversation engine

`AbstractConversation<T>` discovers topics at construction time, sorts them by `order` then `key`, and drives the flow through `play()`:

. Select the next playable topic (`nextTopic()`)
. Invoke `topic.play()` → typically `doPlay()` → `TalkativeBot.ask()`
. On user input, `topic.onInput(SelectedAnswer)` runs, pending state is deleted, then `play()` continues
. Close when no topics remain playable

`Facts` (`LinkedHashMap<String, Object>`, Jackson-serializable) carry business state and framework markers (`__talkative.topic.<key>.closed`, `__talkative.start.*`).

=== Conversation runtime

`ConversationRuntime` is an in-memory, keyed resource bag for *infrastructure* a conversation type needs while it runs — HTTP clients, repositories, API facades, and similar beans. It is **not** where durable conversation state lives.

==== How it is created and attached

. Register a `ConversationRuntimeInitializer` (Spring bean or manual wiring) that `supports` your conversation class and builds a `ConversationRuntime` (typically via `DefaultConversationRuntime.builder()`).
. On every `play()` and every inbound `handle()` resume, `TalkativeBot` calls `hydrateConversationRuntime()`:
.. `ConversationRuntimeRegistry.getOrInitialize(conversationType, initializer)` returns a runtime for that conversation type (creating it once per type on first use).
.. The runtime is injected into the conversation via `RuntimeAwareConversation.setRuntime()`.

Conversation objects themselves are often short-lived: they are created by `ConversationFactory`, run a step, and may be discarded until the next message. The runtime outlives any single conversation instance on that JVM.

==== Per application instance, not distributed

`ConversationRuntimeRegistry` is a local `ConcurrentHashMap` inside the running process. Each application instance (JVM, pod, or node) maintains its own registry.

* No cluster-wide runtime cache or replication is required.
* No coordination protocol is needed to share runtime objects across nodes.
* After a service restart, runtimes are lazily re-created on the next `getOrInitialize` for that conversation type.

This model fits deployments where *durable* progress is carried by `PendingInteractionStore` and `Facts`, while *ephemeral* infrastructure is rebuilt cheaply on each instance.

==== Safe across async hops, scaling, and restarts

Human-in-the-loop flows are inherently asynchronous: ask on one request, resume minutes later on another thread, another pod, or after a redeploy.

| Scenario | Runtime behavior | Where durable state must live |
|==========|==================|===============================|
| User answers after a delay (same JVM) | Conversation recreated; same local runtime reused for that conversation type | `Facts` restored from `PendingInteraction` |
| Load-balanced cluster (Redis/JPA store) | Any node can resume; that node hydrates *its own* local runtime for the conversation type | `Facts` in the pending interaction record |
| Horizontal scale-out | New pods initialize runtimes on demand; no shared runtime service | `Facts` + store TTL |
| Service restart | In-memory runtimes are empty until first use; conversations resume from the store | `Facts` + store TTL |

The runtime is safe for these hops because it holds only *replaceable infrastructure*, not conversation-specific business outcomes. If a `WebClient` or repository is recreated after restart, the flow still continues as long as `Facts` (and the pending interaction snapshot) describe what step the user is on.

==== One runtime per conversation type, per JVM

Within a single application instance, all active conversations of the same type (e.g. every `CheckoutConversation` on that node) share one `ConversationRuntime` for that type. That is intentional: it avoids opening a new connection pool or client per user session.

Do **not** store per-user or per-session durable data in the runtime — use `Facts` instead, so state survives:

* async gaps between question and answer;
* resumption on a different node (with a shared pending store);
* class recreation after rename/deploy (for in-flight interactions, subject to conversation class name stability).

==== Facts vs runtime — what goes where

[cols="2,3", options="header"]
|===
| Store in `Facts` | Store in `ConversationRuntime`

| User choices, workflow step, business identifiers
| `WebClient`, JDBC templates, gRPC stubs, service clients

| Anything serialized into `PendingInteraction`
| Anything expensive to construct but safe to share per conversation type

| State that must survive TTL-bound pending storage
| Stateless or idempotent infrastructure helpers
|===

`Facts` are Jackson-serializable and copied into `PendingInteraction` when `TalkativeBot.ask()` runs. Treat them as the source of truth for *what* the conversation knows. Treat the runtime as *how* the conversation talks to the outside world on this JVM.

==== Example

The joke factory demo (`JokeFactoryConversationRuntimeInitializer`) registers a `WebClient` and joke API helper in the runtime. Topic code reads it via `getRuntime().get(key, JokeFactoryRuntime.class)`. Joke type, action, and joke id live in `Facts` so the punchline step can resume correctly after the user replies.

== Message Flow

=== Inbound path

[source]
----
[User / External system]
        │
        ▼
┌───────────────────┐     ┌──────────────────────────────┐
│ InputChannel      │     │ SpringCloudStreamInputConsumer│
│ (e.g. Console)    │     │ Consumer<IncomingMessage>     │
└─────────┬─────────┘     └──────────────┬───────────────┘
          │                                │
          └──────────────┬─────────────────┘
                         ▼
              TalkativeBot.handle(IncomingMessage)
                         │
         ┌───────────────┴────────────────┐
         │                                │
    pending found?                   no pending
         │                                │
         ▼                                ▼
  resumeConversation()      ConversationStartRegistry.resolve()
         │                                │
         │                         startConversation()
         └───────────────┬────────────────┘
                         ▼
         ConversationFactory.create(FQCN, address)
         restore Facts, hydrate ConversationRuntime
                         ▼
              topic.onInput() then conversation.play()
              — or — conversation.play() on fresh start
----

=== Resume sequence

When a `PendingInteraction` exists for the message's `ConversationAddress.persistenceKey()`:

. Load interaction from store (memory, Redis, or database)
. Recreate conversation via `ConversationFactory`
. Clear facts and replay snapshot from pending interaction
. Resolve topic by `currentTopicKey`; call `onInput(SelectedAnswer)`
. Delete pending interaction
. Call `conversation.play()` to advance the flow

For choice questions, `DefaultOptionSelector` matches option *value* (integer parse) or *text* (case-insensitive). Invalid choices throw `IllegalArgumentException`.

=== Outbound path

`TalkativeBot.ask()` builds a `PendingInteraction` (address, conversation FQCN, topic key, question, facts snapshot), saves it with configured TTL, then sends `OutgoingMessage.question(...)` through `OutputChannelRegistry`.
The first `OutputChannel` where `supports(address)` returns true handles delivery.

=== Address and persistence key

`ConversationAddress` carries `channel`, `userId`, and optional `sessionId`.
For non-legacy addresses, `persistenceKey()` prefers `sessionId` → `userId`, so one pending interaction exists per user/session address.
`channel` is not arbitrary provider metadata.
It must map to a supported TalkativeBot input/output channel for the application, because outbound delivery uses `OutputChannel.supports(address)` to select the transport.
For example, built-in output channels support values such as `console`, `spring-cloud-stream`, or `stream`.

`conversationId` is still accepted as a legacy constructor/JSON field for backward compatibility with existing integrations and persisted pending interactions.
New integrations should not use it for workflow lanes or platform thread ids.
Platform-specific conversation, session, or message ids belong in `IncomingMessage.channel` (`ChannelInfo`), and first-class workflow separation should be handled by a scoped conversation model.
Provider-specific surfaces such as Facebook Messenger, WhatsApp, or web checkout should also be described in `ChannelInfo` unless the application has registered matching TalkativeBot channels for those values.

=== Incoming message envelope

`IncomingMessage` is the inbound event envelope that client integrations pass into `TalkativeBot.handle(...)`.
The minimal shape is still `ConversationAddress` + `text`, which keeps existing simple integrations working.
Richer clients can also include channel, external identity, referral, metadata, and raw payload references without overloading `ConversationAddress` or placing transport details inside message text.

This distinction matters because `ConversationAddress` is used for routing and pending interaction lookup.
It should identify where a reply belongs.
Its `channel` must identify a TalkativeBot channel that can transport replies.
It should not become the place for client-specific details such as a Facebook page id, webhook message id, campaign referral, display name, phone number, external provider conversation id, provider channel, or raw payload pointer.

[cols="1,3", options="header"]
|===
| Field | Purpose

| `id`
| Unique inbound event id generated by the client integration or by TalkativeBot when the simple constructor is used.

| `address`
| Conversation routing and persistence address. This is what pending interaction lookup uses.

| `text`
| Human-readable message text or command text. Non-text events should still provide a safe text value for resolver/topic compatibility.

| `receivedAt`
| Time the integration received or created the inbound event.

| `eventType`
| Optional event category supplied by the client integration, for example `message`, `postback`, `location`, or `delivery_status`.

| `channel`
| Optional `ChannelInfo` with provider/channel details such as provider name, client channel, integration name, external conversation id, external session id, and external message id.

| `externalIdentity`
| Optional `ExternalIdentity` for the user/customer identity known by the client integration.

| `referral`
| Optional `ReferralContext` for campaign, deep-link, source, or target information that caused the conversation to start or continue.

| `metadata`
| Optional serializable key-value metadata for integration-specific values that do not deserve first-class fields yet.

| `rawPayloadReference`
| Optional pointer to a stored raw payload, log entry, blob key, or trace id. Store a reference instead of stuffing a large webhook body into the message.
|===

`ChannelInfo` describes the source channel from the client integration's point of view:

[cols="1,3", options="header"]
|===
| Field | Meaning

| `provider`
| External provider or platform, for example `facebook`, `whatsapp`, `slack`, or `web`.

| `channel`
| Provider channel or product surface, for example `messenger`, `business_chat`, or `web_checkout`.

| `adapter`
| Name of the application integration component that translated the external event into `IncomingMessage`.

| `conversationId`
| External provider conversation/thread id, if available.

| `sessionId`
| External provider session id, if available.

| `messageId`
| External provider message/event id, if available.
|===

`ExternalIdentity` describes the user as known by the client integration:

[cols="1,3", options="header"]
|===
| Field | Meaning

| `provider`
| Identity provider or platform that supplied the identity.

| `externalUserId`
| Provider-specific user id.

| `displayName`
| Display name supplied by the provider or client integration.

| `phone`
| Phone number when the integration has a trustworthy user phone.

| `email`
| Email address when the integration has a trustworthy user email.
|===

`ReferralContext` carries optional source information:

[cols="1,3", options="header"]
|===
| Field | Meaning

| `type`
| Referral category, for example `ad`, `share`, `deep_link`, or `qr`.

| `sourceId`
| Provider/source identifier.

| `sourceUrl`
| Source URL, if available.

| `targetType`
| Type of thing the referral points to, for example `product`, `order`, or `campaign`.

| `targetId`
| Identifier of the target.

| `campaignId`
| Campaign identifier.

| `metadata`
| Serializable referral-specific details.
|===

== Core Concepts

=== Conversations

A conversation orchestrates an ordered graph of topics. Subclass `AbstractConversation<T>` and optionally override:

* `onTopicPlayed(ConversationTopic)` — after a topic finishes without closing the conversation
* `onConversationClosed()` — when all topics are exhausted or closed
* `onAlreadyClosed()` — if `play()` is invoked on a closed conversation

**Required constructor convention:** public `(TalkativeBot bot, ConversationAddress address)` for `ReflectionConversationFactory`.

Conversations can be started manually:

[source,java]
----
talkativebot.play(new SaleConversation(talkativebot, consoleAddress));
----

Or triggered automatically via `ConversationStartResolver` when inbound messages do not match a pending interaction.

=== Topics

Topics are the atomic units of dialogue. Each topic:

* Declares metadata via `@Topic` (`key`, `name`, `description`, `conversation`, `canReplay`, `order`, `next`)
* Implements `doPlay(Facts)` to ask questions or perform side effects
* Handles answers in `onInput(SelectedAnswer)`
* Uses `canPlayWithFacts(Facts)` for conditional branching

Extend `AbstractTopic` (starter module) for helpers: `ask()`, `fact()`, `close()`, closure fact management.

**Topic registration:** `TopicScanner.scan(conversationType)` returns descriptors; instances are created via `TopicFactory` and registered in a `LinkedHashMap` keyed by topic key.

**Default key:** decapitalized simple class name when `@Topic.key` is blank.

=== Topic progression: `next` vs `order`

[cols="1,3", options="header"]
|===
| Mechanism | Behavior

| `order` + `key`
| Topics are registered sorted by `order`, then `key`. Initial selection and fallback use the first *playable* topic in that order.

| `next`
| After the current topic, if `getNextTopicKey()` is set and the target topic `isPlayable(facts)`, that topic runs next — *before* order-based fallback.

| `canReplay`
| When `true`, a closed topic (`__talkative.topic.<key>.closed` fact set) can play again.

| `canPlayWithFacts`
| Override to gate topics on business facts (e.g. skip shipping when pickup is selected).
|===

`order` and `next` work together: `next` selects the immediate successor when the target topic is playable; `order` governs registration, the first topic when none is current, and fallback when `next` is unset, invalid, or not playable.

=== Channels

Channels adapt transport to the framework's message model:

* `InputChannel` — `start(InputMessageHandler)`, `stop()`; pushes `IncomingMessage` to the bot
* `OutputChannel` — `supports(ConversationAddress)`, `send(OutgoingMessage)`
* `InputChannelLifecycle` (starter) — `SmartLifecycle` that starts all `InputChannel` beans when `channels.enabled=true`

Built-in and starter-provided channels:

[cols="2,3", options="header"]
|===
| Implementation | Channel id / notes

| `ConsoleInputChannel` / `ConsoleOutputChannel`
| `console` — stdin/stdout for local development

| `SpringCloudStreamOutputChannel`
| `spring-cloud-stream` or `stream` — via `StreamBridge`

| `SpringCloudStreamInputConsumer`
| `Consumer<IncomingMessage>` bean — *not* an `InputChannel`; wired manually
|===

Spring Cloud Stream is not auto-registered; applications declare stream beans explicitly (see `example-stream-redis/agent-one`).

=== Questions and answers

`Question` supports text and choice types (`QuestionType`). Choice questions use `Option` (value + display text).
`SelectedAnswer` wraps the matched option (if any), raw text, and the original `IncomingMessage`.

== Persistence

=== PendingInteraction model

A pending interaction captures everything needed to resume after an async human reply:

* `ConversationAddress`
* Conversation type (FQCN string)
* Current topic key
* `Question` being asked
* `Facts` snapshot
* Timestamps and TTL metadata

=== Store implementations

[cols="2,2,3", options="header"]
|===
| Store | Property value | Implementation

| In-memory
| `memory` (default)
| `InMemoryPendingInteractionStore` — `ConcurrentHashMap`, expiry checked on read

| Redis
| `redis`
| `RedisPendingInteractionStore` — key `talkativebot:pending-interaction:{persistenceKey}`, Redis TTL

| Database
| `database`
| `JpaPendingInteractionStore` — `PendingInteractionEntity` with JSON payload and `expiresAt`
|===

Misconfiguration is fail-fast: selecting `redis` or `database` without the required beans throws at startup via conditional failure beans.

*Limitations:*

* One pending interaction per `persistenceKey()` — no stacked questions
* JPA `deleteExpired()` exists but is not scheduled automatically
* Ongoing or persisted conversations break if conversation classes are renamed

== Spring Boot Integration

=== Auto-configuration

Registered in `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`:

[source]
----
TalkativeBotConversationRuntimeAutoConfiguration  (before main)
TalkativeBotRedisAutoConfiguration                (before main, conditional)
TalkativeBotJpaAutoConfiguration                  (before main, conditional)
TalkativeBotAutoConfiguration
TalkativeBotConsoleAutoConfiguration
----

`TalkativeBotAutoConfiguration` provides (when not overridden):

* `TalkativeBot` bean
* `SpringTopicScanner`, `SpringTopicFactory`
* `ReflectionConversationFactory`
* `OutputChannelRegistry`, `ConversationStartRegistry`
* `InputChannelLifecycle` when channels enabled
* Store bean selected by `pending-interaction.store`

`TalkativeBotConsoleAutoConfiguration` registers console channels when `channels.console-enabled=true`.

=== Required application conventions

* Set `atchurey.tools.talkativebot.topic-base-package` to the package containing `@Topic` classes
* Conversation classes: public constructor `(TalkativeBot, ConversationAddress)`
* Topic classes: Spring `@Component` or constructor `(Conversation<?>)` / no-arg
* For stream integration: declare `SpringCloudStreamOutputChannel` and `Consumer<IncomingMessage>` beans

=== Core-only usage

Without the starter, you must supply implementations of `TopicScanner` and `TopicFactory` (core provides `ReflectionTopicFactory` only).
`ConsoleInputChannel` and `ConsoleOutputChannel` are available in core; `InMemoryPendingInteractionStore` is the default store.

== Examples

=== example-console (checkout flow)

Demonstrates:

* Manual `TalkativeBot.play()` via `SaleConversationRunner`
* In-memory pending store
* Console I/O with configured `console-address`
* Topic chain: `greetings` → `cart_review` → `delivery_method` → `shipping_address` → `payment_method`

Patterns shown: `canPlayWithFacts` gating, fact accumulation across topics, `onConversationClosed` logging, abandon vs close in `onInput`.

*Known gap:* `PaymentMethodTopic` declares `next = "complete_sale"`, but no `CompleteSaleTopic` class exists in the module — the flow logs a warning and falls back to order-based selection.

=== example-stream-redis (joke factory)

A two-process distributed demo:

**agent-one** — full TalkativeBot + Redis + RabbitMQ:

* `JokeFactoryConversation`, `JokeFactoryTopic`, `JokeFactoryConversationStartResolver` (`/start`)
* `JokeFactoryConversationRuntimeInitializer` — `WebClient` to the Official Joke API
* Stream bindings: questions to `agent-two-input`, answers from `agent-one-input`
* Redis pending store (`ttl=20m`)

**agent-two** — core types only, simulates an external chat UI:

* Consumes `OutgoingMessage`, logs setup/punchline, auto-replies with first option value
* Sends `IncomingMessage` back via `StreamBridge`

*Walkthrough:*

. User sends `/start` → resolver starts `JokeFactoryConversation`
. `JokeFactoryTopic.doPlay` calls joke API, asks choice question (setup + "What?" option)
. Pending interaction saved in Redis; message sent to agent-two
. Agent-two replies with joke id → `onInput` sets `action=deliver_punchline`
. Topic replays, fetches punchline, asks text question
. `@Topic(canReplay=true)` allows another joke cycle

Requires RabbitMQ and Redis (see `application.yml` in each agent).

== Testing

=== talkativebot-core

~18 test classes using JUnit 5, AssertJ, and Mockito.

Coverage includes: `TalkativeBot` start/ask/resume flow, `AbstractConversation` topic ordering and `next` links, channel registries, `Facts`, runtime registry, console channel behavior.

*Gaps:* No integration tests for Redis, JPA, or Spring Cloud Stream.

=== talkativebot-spring-boot-starter

Slice tests with `ApplicationContextRunner` verify default beans, property mapping, memory default, fail-fast for misconfigured `redis`/`database` stores, and console conditional registration.

=== Examples

`@SpringBootTest` context-load tests only — no end-to-end conversation assertions.

== Design Decisions and Trade-offs

[cols="2,2,2", options="header"]
|===
| Decision | Benefit | Trade-off

| Spring-free core
| Portable, unit-testable without Boot
| Topic scanning and DI require starter or custom wiring

| Pending interaction per address
| Simple resume model
| Cannot stack multiple open questions per address

| Conversation recreation by class name
| Serializable pending state
| Ongoing or persisted conversations break if classes are renamed

| Facts-based topic closure
| Survives pending store round-trips
| `__talkative.*` keys in fact namespace

| Runtime per conversation type, per JVM
| Reuse expensive clients; no distributed runtime cache
| Must not hold per-user durable state — use `Facts` instead

| First matching output channel
| Simple routing
| Bean registration order matters

| `AbstractTopic` in starter
| Rich helpers (`ask`, `fact`, `close`)
| Topic base class not in core module
|===

== Known Limitations

* `TopicScanner` has no core implementation — Spring starter or custom scanner required
* Spring Cloud Stream input bypasses `InputChannelLifecycle`
* Invalid choice answers throw `IllegalArgumentException` with no structured error channel
* JPA expired-row cleanup is not scheduled
* Redis store expects a `RedisOperations<String, Object>` bean

== TODO

Upcoming work, known gaps to close, and planned features. Items are listed in rough priority order.

. *Auto-register Spring Cloud Stream channels* — Today, Spring Cloud Stream is not auto-registered; applications must declare `SpringCloudStreamOutputChannel` and `Consumer<IncomingMessage>` beans explicitly (see `example-stream-redis/agent-one`). Add starter auto-configuration so stream input/output channels are registered when Spring Cloud Stream is on the classpath, aligned with how console channels are registered via `TalkativeBotConsoleAutoConfiguration`.
. *Integration tests for Redis, JPA, and Spring Cloud Stream* — Core and starter slice tests cover defaults and fail-fast configuration; add end-to-end tests against real (or Testcontainers) Redis, JPA, and stream bindings to verify pending interaction persistence and message flow.
. *TopicScanner implementation in core* — `TopicScanner` is an interface only in `talkativebot-core`; topic discovery today requires `SpringTopicScanner` from the starter or a custom scanner. Add a framework-neutral classpath scanner in core so non-Spring applications can discover `@Topic` classes without the starter.
. *Structured errors for invalid choice answers* — Invalid option replies throw `IllegalArgumentException` with no channel-friendly error response. Return a structured error (e.g. via `OutgoingMessage`) so users can retry without an unhandled failure.
. *Scheduled JPA expired-row cleanup* — `JpaPendingInteractionStore.deleteExpired()` exists but is never scheduled. Add a periodic job or Boot scheduling integration to purge expired pending interactions from the database.

== Quick Start

=== Manual conversation start

[source,java]
----
@Autowired
TalkativeBot talkativebot;

ConversationAddress consoleAddress = new ConversationAddress(
    "console",
    "console-user-1",
    "console-session-1"
);
talkativebot.play(new SaleConversation(talkativebot, consoleAddress));
----

=== Automatic start via resolver

[source,java]
----
@Component
public class SaleConversationStartResolver implements ConversationStartResolver {

    @Override
    public Optional<ConversationStartRequest> resolve(IncomingMessage message) {
        if (!"/start".equalsIgnoreCase(message.getText().trim())) {
            return Optional.empty();
        }

        return Optional.of(new ConversationStartRequest(
                message.getAddress(),
                SaleConversation.class.getName(),
                "/start",
                Map.of(
                        "source_channel", message.getAddress().getChannel(),
                        "external_user_id", valueOrEmpty(message.getAddress().getUserId())
                )
        ));
    }

    private Serializable valueOrEmpty(String value) {
        return value == null ? "" : value;
    }
}
----

=== Conversation implementation

[source,java]
----
public class SaleConversation extends AbstractConversation<String> {

    public SaleConversation(TalkativeBot bot, ConversationAddress address) {
        super(bot, address);
    }

    @Override
    protected CompletableFuture<String> onTopicPlayed(ConversationTopic topic) {
        if (isClosed()) {
            return onConversationClosed();
        }
        return CompletableFuture.completedFuture("Played topic: " + topic.getKey());
    }

    @Override
    protected CompletableFuture<String> onConversationClosed() {
        return bot.reply("Sale conversation completed.");
    }
}
----

=== Topic implementation

[source,java]
----
@Topic(
    key = "payment_method",
    name = "Payment Method",
    description = "Choose your payment method",
    conversation = SaleConversation.class,
    canReplay = true,
    next = "complete_sale",
    order = 4
)
public class PaymentMethodTopic extends AbstractTopic {

    public PaymentMethodTopic(Conversation<?> conversation) {
        super(conversation);
    }

    @Override
    protected boolean canPlayWithFacts(@NonNull Facts facts) {
        return true;
    }

    @Override
    protected void doPlay(Facts facts) {
        Question question = new Question("Choose your payment method.",
                new Option[]{
                        new Option(0, "CARD"),
                        new Option(1, "CASH")
                });
        getBot().ask(conversation, this, question);
    }

    @Override
    public void onInput(SelectedAnswer selectedAnswer) {
        logger.info("User selected payment method: {}", selectedAnswer.getText());
    }
}
----
